# 项目宪法

> 类型：contract
> 适用范围：本仓库全部代码、文档和 AI Agent 行为
> Canonical sources：`AGENTS.md`、`README_First.md`、`.ai/architecture/`、`.ai/decisions/`

本文件是本项目的最高规范权威，规定抽象、单向门决策、验证与 gate 分层、完成状态、兼容层治理和重构治理的长期规则。日常执行步骤以 `AGENTS.md` 为准；当 `AGENTS.md`、README 或任何其他文档与本文件的原则冲突时，以本文件为准。

本文件只写宪法级规则：跨目录、跨技术栈、长期不变、违反后果严重。单次修改记录写 `.ai/changes/`，架构事实写 `.ai/architecture/`，具体决策写 `.ai/decisions/`，本文件不重复它们。

---

## 第一章 抽象治理

1. **抽象必须由重复证明，不得由预测创造。** 同类逻辑出现第二次时允许提取，出现第三次时必须评估提取；为"未来可能需要"而预建的抽象层、插件机制、配置项一律禁止。
2. **抽象以薄封装为默认形态。** 本项目的既有范式是 `api_v1_client.rs` 式薄客户端和 `grid_list_sessions` 式薄 Tauri command：只做协议解包、鉴权注入和错误归一，不吸收业务逻辑。新抽象应先对照这一范式。
3. **状态切片必须隔离。** 前端新增全局状态时，按 Workspace Grid 的 zustand 切片先例建立独立 store，不得把新状态混入既有 controller 或已有切片；一个切片对应一个可独立说明职责的领域。
4. **跨技术栈契约只允许有一个权威定义。** Shell（Rust/TS）与 Bridge（Go）之间的 envelope、locator 文件、token 传递方式，其权威定义在源码和可执行契约中，各端只做映射，不得各自另造一份"等价"结构。
5. **删除劣质抽象优先于绕过它。** 发现只有一个调用方、或调用方都在绕开它的抽象（如已删除的 `ControlCenterMetricCard` 先例），应删除而非继续包装。

## 第二章 单向门决策

单向门指事后回退成本远高于事前审慎成本的决策。跨越单向门前必须在 `.ai/decisions/` 建立 ADR 并达到 accepted 状态；双向门决策直接执行并记入 `.ai/changes/` 即可。

本项目的单向门至少包括：

1. **持久化数据结构。** SQLite migration 只增不改：新增版本号、新增表或索引，不修改、不删除既有字段语义。持久化的前端 state 结构（如 Grid persisted state）同理，变更必须附带加载期归一化兼容路径。
2. **序列化契约。** Tauri command 名称、command 输入输出的序列化类型、Bridge admin envelope（`{ ok, data, error, requestId }`）、`/api/v1` envelope 映射、`kimi_runtime_locator.json` 字段，一旦发布即为契约；只允许增量扩展，不允许改名或改语义。
3. **秘密的存放与传递位置。**（详见第三章，其规则本身即宪法级，变更须走修宪程序。）
4. **安装与发布表面。** installer 主链路（官方 Windows installer / `kimi upgrade`）、NSIS/MSI 产物路径、bundled sidecar 路径的变更。
5. **对外依赖的引入。** 新增运行时依赖（npm 包、crate、Go module）属于单向门的弱形式：不强制 ADR，但必须在变更记录中说明为何既有依赖不够用。

判断规则：拿不准是不是单向门时，按单向门处理。

## 第三章 安全不变量

以下规则无例外、无豁免，任何任务目标都不构成违反它们的理由：

1. 明文 token、密码、平台密钥、API key **不得**出现在：进程命令行参数、持久化 state、locator 文件、README、`.ai/` 任何文档、日志和诊断包。
2. 秘密只通过环境变量或 token file 传递；对外展示一律脱敏（redacted）。
3. 所有承接子进程 stdout/stderr 的路径必须经过 redactor 后再落盘；新增日志出口时，脱敏接入是该出口"完成"的必要条件，不是后续优化。
4. 前端 persisted state 不得保存 token、cookie 或含 `#token=` 的 URL fragment；运行时组装的 bootstrap URL 只存在于内存。
5. 发现违反本章的既有代码时，修复它的优先级高于当前任务。

## 第四章 验证与 gate 分层

验证分四层，每层通过只授权声明该层的结论，不得越层宣称：

| 层级 | 内容 | 授权的结论 |
|---|---|---|
| G0 类型/编译 | `tsc --noEmit`、`cargo check`、`go vet` | 代码结构成立 |
| G1 本地测试 | `pnpm test`、`cargo test`、`go test ./...` | 已覆盖行为未回归 |
| G2 CI gate | 仓库 CI 的 Go/Rust/TS gate、clippy | 变更可合入 |
| G3 手工发布门 | 真实凭证 IM 回归、安装包 lifecycle、诊断包脱敏核验 | 可发布 |

规则：

1. 具体命令的权威清单在 `.ai/architecture/verification-gates.md`，本文件不复制命令。
2. 某层因环境缺失无法执行（如缺 gcc 无法跑 race、缺真实凭证无法跑 IM 回归）时，必须在变更记录中显式标注 blocked 及补跑环境，不得静默降级为"已验证"。
3. 触碰序列化契约、migration、秘密路径的变更，G1 是最低门槛；只过 G0 不得合入。
4. 新增长期功能面（新 channel adapter、新 runtime adapter、新安装任务）时，必须同步给出它落在哪一层 gate、由哪条命令或哪个手工用例覆盖；无验证入口的功能面不接受。

## 第五章 完成状态

1. 完成状态只有四种合法词汇：**已实现**（代码在，G0 过）、**已验证**（对应层级 gate 过）、**blocked**（明确缺什么环境或凭证）、**已发布**（G3 过且产物出）。禁止使用"应该没问题""基本完成""已生产可用"等无 gate 支撑的表述。
2. 任何"已验证"声明必须可追溯到 `.ai/changes/` 中的验证方式条目。
3. 部分完成必须拆开陈述：哪些子项到了哪个状态，而不是给整体一个模糊状态。既有实践（如"Go test/vet 已通过，race 需在 CI 补跑"）是标准写法。
4. 任务在 blocked 状态下可以收口，但收口记录必须包含解除 blocked 的具体条件。

## 第六章 兼容层治理

1. **兼容层出生即登记。** 任何为旧行为保留的路径——旧双窗 localStorage 键、Bridge 裸 JSON envelope 兼容、Go sidecar 旧 flag fallback、legacy uv/Python repair 任务——都必须在 `.ai/architecture/current-state.md` 或对应 ADR 中被点名为兼容层，注明它兼容的是什么。
2. **兼容层必须有退出条件。** 登记时同时写明退出条件，形式为可判定的事实（如"所有持久化用户迁移完成一个发布周期后""新主路径通过 G3 一次后"），不接受"以后再说"。
3. **兼容层不得长出新功能。** 兼容路径只维持旧行为，新特性只在主路径实现；发现新代码开始依赖兼容层时，视为架构违规，触发第七章重构评估。
4. **退出兼容层是正式变更。** 满足退出条件后移除兼容层，需通过 G1 及以上验证，记入 `.ai/changes/`，并同步清理 `current-state.md` 中的登记。
5. 未登记的兼容逻辑视为技术债，Agent 在触及它时有义务补登记。

## 第七章 重构治理

1. **重构触发标准**，满足任一即应评估重构，并在变更记录中给出做或不做的理由：
   - 同类逻辑第三次出现；
   - 修改一处必须同步改动三处以上非契约代码；
   - 代码违反目录 README 声明的职责边界或依赖边界；
   - 存在零调用方的导出、组件或命令；
   - 新代码开始依赖兼容层（见第六章）。
2. **重构必须行为保持。** 重构提交不改变产品行为、UI 文案、序列化类型、Tauri command 名称和 CSS 对外类名；若重构不得不触碰这些，它就不是重构，按功能变更走对应的单向门流程。
3. **重构与功能变更分离。** 顺手重构限制在当前任务的影响范围内；超出范围的重构拆为独立任务，不与功能变更混在同一次提交里。
4. **重构的完成标准是 G1。** 行为保持的证明方式是既有测试全绿加类型检查通过；无测试覆盖的区域先补最小测试再重构，或在记录中显式声明风险。
5. **重构不得以更新文档的方式掩盖行为变化。** README 与代码冲突时的处理遵循 `AGENTS.md` 的冲突规则：先指出，再决定改哪边。

## 第八章 修宪程序

1. 本文件只在宪法级规则本身变化时修改；日常规程变化改 `AGENTS.md`，事实变化改 `.ai/architecture/`。
2. 修改本文件必须：在 `.ai/decisions/` 建立说明动机与影响的 ADR，在 `.ai/changes/` 记录，并检查 `AGENTS.md` 与 `README_First.md` 中对本文件的描述是否需要同步。
3. 第三章安全不变量的任何放宽，除上述程序外还必须逐条说明替代防护；不存在替代防护的放宽不予接受。
4. 本文件与任何后续文档冲突时，冲突本身应被视为信号：要么修宪，要么修正那份文档，不允许两者长期并存。
