## 2026-08-19-10 - 修复 Windows LAN 虚拟网卡地址误展示

- 用户目标：修复 Windows 控制中心同时显示真实局域网地址与不可达 WSL/Hyper-V 内部地址、并为两者都提供二维码的问题。
- 涉及目录：`apps/kimi-shell/src-tauri`、Shell README、Native LAN ADR 与架构事实。
- 修改内容：复用既有 `windows` crate 的 IpHelper/Ndis/WinSock features，通过 `GetAdaptersAddresses` 将 `get_if_addrs` 返回的 Windows GUID 映射到 FriendlyName、Description、接口类型、运行状态和 IPv4 网关；过滤停用、隧道、VPN 及无网关内部虚拟交换机，保留物理网卡与拥有真实网关的 Hyper-V 外部交换机；新增 GUID、WSL、物理 Wi-Fi、外部交换机、VPN 和停用网卡回归测试。
- 修改原因：`get_if_addrs 0.5.3` 在 Windows 使用 `AdapterName` GUID 且跳过 FriendlyName，原有基于 `vEthernet` / `Hyper-V` 名称的过滤无法命中生产值，导致 `172.27.*` 一类 host-only/NAT 地址被投影为手机可访问地址。
- 本次已消除的不确定性：确认 UI 只是逐项展示 Rust 地址投影；确认错误不来自二维码或 Kimi 多实例；确认现有 `windows 0.61` 可直接提供所需系统 API，无需新增 crate。
- 本次采用的关键假设：拥有 IPv4 网关的 Hyper-V 外部交换机可能承载宿主真实 LAN 地址，因此不能按 `vEthernet` 名称一律排除；Windows `AdapterName` 在两次 `GetAdaptersAddresses` 枚举间可用规范化 GUID 关联。
- 剩余不确定性：真实 Windows 上 WSL2/Hyper-V/Docker 多网卡组合、Windows 防火墙与手机访问仍需 G3 安装包复验；macOS 主路径未改变。
- 影响范围：只改变 Windows LAN 地址的展示候选与友好名称；不改变 wildcard listener、Token、二维码内容、IPC schema、持久化状态或 macOS 枚举行为。
- 验证方式：`cargo fmt --all -- --check`、`cargo check --locked`、`cargo clippy --locked --all-targets -- -D warnings` 与全量 305 Rust tests 通过；新增 Win32 API 代码以只依赖 `windows 0.61` 的 `x86_64-pc-windows-msvc` 最小 crate 交叉检查通过。完整工程 Windows 交叉检查在本机因既有 `ring`/`lzma-sys` 缺少 MSVC C 标准库头文件而 blocked，需 Windows CI/实机补跑。
- 是否更新 README：是；登记 Windows LAN 网卡元数据筛选职责。
- 是否更新 `.ai/architecture`：是；登记 Windows 地址投影事实。
- 是否需要新增或更新 `.ai/decisions`：是；增量修正 Accepted Native LAN ADR 的 Windows 枚举策略，不改变安全边界。
- 后续注意事项：不得通过排除整个 `172.16/12` 网段修复虚拟网卡问题；发布前需在启用 WSL2/Hyper-V 的 Windows 机器确认 UI 只显示真实 LAN 入口，并用同网手机访问。
