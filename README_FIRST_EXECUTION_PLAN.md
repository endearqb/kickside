# README First 项目上下文系统：需求与执行方案

> 类型：archive
> 状态：历史初始化方案，非日常规则入口。
> 当前执行规则以 `AGENTS.md`、`.ai/CONSTITUTION.md` 和 `README_First.md` 为准；本文档只保留当时的实施背景。

> 本文档用于交给 Codex 在现有项目中执行。目标是在仓库中建立一套“README First”协作机制：AI 在执行任何文件查询、创建、修改、删除前，必须先读取全局规则和相关目录 README；执行后必须把有长期维护价值的信息写回 README，把具体修改记录写入 `.ai/changes/`。

---

## 0. 给 Codex 的执行指令

你现在要在当前仓库中实施本方案。请严格按本文档执行，不要自行扩大范围。

本次任务的核心目标是：

1. 创建或更新仓库根目录 `AGENTS.md`，让 Codex 和其他 AI Agent 以后默认遵守 README First 规则。
2. 为项目中的关键目录创建或补全 `README.md`，让每个关键目录都有清晰的职责说明、维护约定和 AI 操作提示。
3. 创建 `.ai/changes/` 用于记录每次 AI 修改；创建 `.ai/decisions/` 用于记录长期架构决策。
4. 本次任务只建立文档体系，不重构业务代码，不改变功能行为，不引入依赖。
5. 如果仓库中已经存在 `AGENTS.md` 或目录 README，不要直接覆盖；必须保留原有有效内容，在此基础上合并、补充、整理。

执行完成后，请输出一份变更报告，至少包含：

- 新增文件列表。
- 修改文件列表。
- 被跳过的目录及原因。
- 发现的 README 与代码不一致之处。
- 本次是否修改了业务代码，预期答案应为“否”。
- 建议用户后续人工确认的事项。

## 1. 背景与问题

在 AI 参与项目开发时，常见问题包括：

1. AI 修改文件前没有充分理解目录职责。
2. AI 重复创建已有功能，导致代码结构膨胀。
3. AI 不知道项目中的隐含约定，例如导出规则、依赖边界、测试方式、命名规范。
4. AI 修改完成后没有留下可复用的上下文，下一次任务仍然需要重新摸索。
5. README 和实际代码长期脱节，文档变成摆设。

本方案要建立一套轻量但强约束的项目上下文机制，让 README 成为 AI 的局部操作入口，让 `AGENTS.md` 成为全局行为规则，让 `.ai/changes/` 和 `.ai/decisions/` 成为长期维护记录。

## 2. 目标

### 2.1 主要目标

建立一套“README First”机制，使未来所有 AI Agent 在项目中执行增删改查前，都必须先读取：

1. 根目录 `AGENTS.md`。
2. 根目录 `README.md`。
3. 当前任务涉及路径上的所有相关目录 `README.md`。
4. 与任务直接相关的源代码、配置、测试或文档。

### 2.2 文档目标

实施完成后，仓库中应至少具备以下文档资产：

```txt
project/
├── AGENTS.md
├── README.md
├── .ai/
│   ├── changes/
│   │   └── YYYY-MM-DD.md
│   └── decisions/
│       └── 0001-readme-first-policy.md
├── <关键目录>/
│   └── README.md
└── ...
```

其中：

- `AGENTS.md` 负责约束 AI 行为。
- 根目录 `README.md` 负责项目整体说明。
- 各关键目录 `README.md` 负责局部上下文和维护约定。
- `.ai/changes/` 负责记录具体修改。
- `.ai/decisions/` 负责记录长期决策。

### 2.3 非目标

本次任务不做以下事情：

1. 不修改业务逻辑。
2. 不重构代码结构。
3. 不新增运行时依赖。
4. 不删除已有代码文件。
5. 不改动构建、部署、测试配置，除非只是为了在 README 中说明现状。
6. 不为生成目录、缓存目录、依赖目录创建 README。
7. 不把每一次普通代码修改都写进目录 README。

---

## 3. 核心原则

### 3.1 README 是目录契约，不是流水账

每个目录 README 应回答：

1. 这个目录负责什么？
2. 这个目录不负责什么？
3. 这个目录有哪些核心文件或子目录？
4. 修改这里时必须遵守什么约定？
5. 这里对外暴露什么接口、能力或约定？
6. 修改完成后如何验证？
7. AI 在这里操作时要特别注意什么？

README 不应该记录所有细碎修改。普通修改记录应放入 `.ai/changes/YYYY-MM-DD.md`。

### 3.2 文档必须基于实际代码

创建或补全 README 时，必须先读取该目录下的真实文件，基于实际代码和项目结构总结，不得凭空编造。

如果无法判断目录职责，应明确写出：

```md
> 待确认：当前目录职责需要人工进一步确认。
```

不要为了让文档看起来完整而制造不存在的规则。

### 3.3 局部规则优先

未来 AI 操作时，规则优先级为：

1. `AGENTS.md` 中的全局规则。
2. 距离目标文件最近的目录 `README.md`。
3. 上级目录 `README.md`。
4. 实际代码事实。

如果 README 与代码冲突，应先指出冲突，再决定是更新 README 还是修正代码，不得静默忽略。

### 3.4 记录分层

记录分三层：

1. 普通修改：写入 `.ai/changes/YYYY-MM-DD.md`。
2. 目录职责、约定、公共接口变化：更新对应目录 README。
3. 架构决策、长期技术路线、跨目录约定：写入 `.ai/decisions/`。

## 4. 需要创建或更新的文件

### 4.1 根目录 `AGENTS.md`

如果不存在，则创建。如果已存在，则保留原有有效规则，并合并下面的 README First 规则。

建议内容如下：

````md
# AGENTS.md

本文件定义 AI Agent 在本仓库中的工作规则。任何 AI Agent 在读取、分析、修改、创建或删除项目文件前，都必须遵守以下规则。

## 1. README First 原则

在执行任何操作前，必须先阅读相关 README：

1. 先阅读根目录 `README.md`。
2. 再阅读当前任务涉及目录中的 `README.md`。
3. 如果涉及嵌套目录，必须从上到下阅读路径上的 README。

例如修改：

```txt
src/components/Button/Button.tsx
```

需要依次阅读：

```txt
README.md
src/README.md
src/components/README.md
src/components/Button/README.md
```

如果某一级目录没有 README，则继续阅读其上级目录 README，不得自行假设该目录的约定。

## 2. 局部 README 优先级

当不同 README 中的说明存在冲突时，优先级如下：

1. `AGENTS.md` 中的全局规则优先级最高。
2. 距离目标文件最近的目录 README 优先。
3. 上级目录 README 提供通用背景。
4. 如果规则冲突无法判断，必须在修改前指出冲突，不得静默选择。

## 3. 增删改查规则

### 查询文件或回答问题前

AI 必须先阅读相关 README，再基于 README 和实际文件内容回答。

### 新增文件前

AI 必须确认：

1. 当前目录是否允许新增此类文件。
2. 是否已有类似功能文件。
3. 命名、导出、测试、依赖管理是否符合 README 约定。
4. 新文件是否需要在 README 中补充说明。

### 修改文件前

AI 必须确认：

1. 修改是否违反当前目录的职责边界。
2. 是否影响公共 API、数据结构、状态管理、路由、配置或测试。
3. 是否需要同步修改测试、文档、类型定义或调用方。

### 删除文件前

AI 必须确认：

1. 文件是否仍被引用。
2. 删除后是否需要更新索引文件、导出文件、测试、文档或 README。
3. 删除是否会破坏目录 README 中描述的职责或约定。

## 4. 修改完成后的记录规则

每次完成修改后，AI 必须进行记录。

优先记录在：

```txt
.ai/changes/YYYY-MM-DD.md
```

记录格式：

```md
## YYYY-MM-DD-HH - 简短标题

- 涉及目录：
- 修改内容：
- 修改原因：
- 影响范围：
- 是否更新 README：
- 后续注意事项：
```

只有当本次修改改变了目录职责、架构约定、公共接口、文件组织方式或长期维护规则时，才需要同步更新对应目录的 README。

不要把每一次普通代码修改都写进 README。

## 5. README 更新触发条件

以下情况必须更新对应目录的 README：

1. 新增或删除核心文件。
2. 改变目录职责。
3. 改变公共 API、导出方式、数据结构或模块边界。
4. 新增重要约定。
5. 废弃旧约定。
6. 引入新的依赖、构建方式、测试方式或运行方式。
7. 修改会影响未来 AI 或开发者理解该目录的内容。

以下情况通常不需要更新 README：

1. 修复小 bug。
2. 修改文案。
3. 调整局部样式。
4. 重构内部实现但不改变外部行为。
5. 添加临时日志后又删除。

## 6. README 缺失处理

如果任务涉及的目录没有 README：

1. 先阅读上级目录 README。
2. 再根据目录内现有文件推断目录职责。
3. 如果该目录是重要目录，应先创建 README，再继续修改。
4. 创建 README 时必须基于实际代码，不得凭空编造。
5. 如果无法判断目录职责，必须在修改记录中注明不确定点。

## 7. 禁止行为

AI 不得：

1. 在未阅读相关 README 的情况下修改文件。
2. 绕过目录约定直接新增文件。
3. 删除 README 中标记为核心或受保护的文件。
4. 在 README 中堆积无长期价值的流水账。
5. 修改 README 以掩盖错误实现。
6. 忽略 README 与实际代码之间的冲突。
7. 将密钥、令牌、密码、私有凭据或敏感配置写入 README 或 `.ai/changes/`。

## 8. 当 README 与代码不一致时

如果 README 和实际代码不一致，AI 必须：

1. 明确指出不一致之处。
2. 判断是 README 过时，还是代码偏离约定。
3. 在修改中修复代码或更新 README。
4. 在 `.ai/changes/` 中记录本次修正。

## 9. 标准执行流程

AI 每次执行任务时，应遵循：

```txt
1. 定位任务影响范围
2. 阅读 AGENTS.md
3. 阅读相关路径上的 README
4. 检查现有代码与 README 是否一致
5. 执行必要的增删改查
6. 运行或说明验证方式
7. 更新 README 或 .ai/changes
```
````

### 4.3 `.ai/changes/YYYY-MM-DD.md`

创建目录：

```txt
.ai/changes/
```

创建当前日期记录文件：

```txt
.ai/changes/YYYY-MM-DD.md
```

其中 `YYYY-MM-DD` 使用执行当天所在年月。

初始记录模板：

```md
# YYYY-MM-DD 修改记录

## YYYY-MM-DD-HH - 建立 README First 项目上下文系统

- 涉及目录：
  - 根目录
  - `.ai/`
  - 所有新增或补全 README 的关键目录

  - 创建 `.ai/decisions/` 长期决策记录机制

  - 让 AI 在项目中执行增删改查前先读取相关上下文

- 影响范围：
  - 未来所有 AI 协作任务
  - 项目文档结构
  - 关键目录的维护流程

- 是否更新 README：
  - 是

- 后续注意事项：
  - 普通代码修改写入 `.ai/changes/YYYY-MM-DD.md`
  - 只有长期职责、接口、约定或文件组织变化才写入目录 README
  - 不要为生成目录、依赖目录、缓存目录创建 README
```

### 4.4 `.ai/decisions/0001-readme-first-policy.md`

创建目录：

```txt
.ai/decisions/
```

创建长期决策文件：

```md
# 决策 0001：采用 README First 项目上下文机制

## 背景

AI Agent 在项目中进行文件增删改查时，需要稳定、局部、可维护的上下文。如果只依赖一次性 Prompt 或全局 README，AI 容易忽略目录内的隐含约定，导致误改、重复实现或破坏模块边界。

## 决策

本项目采用 README First 机制：

1. 根目录 `AGENTS.md` 作为 AI 行为总规则。
2. 根目录 `README.md` 作为项目整体说明。
3. 关键目录下的 `README.md` 作为该目录的局部上下文和维护契约。
4. 普通 AI 修改记录写入 `.ai/changes/YYYY-MM-DD.md`。
5. 长期架构决策写入 `.ai/decisions/`。

## 影响

- AI 修改文件前必须先读取相关 README。
- 新增、修改、删除文件时必须检查目录职责和维护约定。
- 修改完成后必须记录。
- README 只记录长期有效的信息，不记录普通流水账。

## 取舍

优点：

- 降低 AI 误改风险。
- 降低重复沟通成本。
- 让目录职责和模块边界显性化。
- 方便新开发者快速理解项目结构。

代价：

- 初期需要补全文档。
- 后续需要维护 README 与代码一致。
- 需要避免过度记录和文档膨胀。

## 后续维护规则

当目录职责、公共接口、依赖边界、核心文件组织或测试方式发生变化时，必须更新对应目录 README。

当只是普通 bugfix、文案、样式或内部实现调整时，只需要写入 `.ai/changes/YYYY-MM-DD.md`，通常不需要更新 README。
```

## 6. 关键目录选择规则

Codex 不应机械地给所有目录创建 README，而应优先识别“关键目录”。

### 6.1 应优先创建 README 的目录

满足以下任一条件的目录，应创建或补全 README：

1. 有独立职责。
2. 经常被开发者或 AI 修改。
3. 存在隐含约定。
4. 文件数量较多，未来维护成本高。
5. 是核心业务、基础设施、配置、测试或公共接口目录。
6. 改错后影响范围较大。

如果某个 `vendor/` 或类似目录是项目手写源码而不是第三方依赖，Codex 可以例外处理，但必须在变更报告中说明原因。

### 6.3 建议的目录识别方法

优先使用 Git 跟踪文件判断目录，而不是扫描所有文件：

```bash
git status --short
git ls-files
```

根据 `git ls-files` 输出构建候选目录列表，避免进入依赖、缓存、构建产物目录。

如果项目不是 Git 仓库，再使用受限的目录扫描，并遵守上面的跳过规则。

## 7. 执行阶段

### 阶段 1：预检查

Codex 应执行：

1. 检查当前目录是否为项目根目录。
2. 读取已有 `AGENTS.md`、根目录 `README.md`、项目配置文件。
3. 查看 Git 状态，确认当前是否已有用户未提交改动。
4. 如果存在未提交改动，不要覆盖；后续修改必须尽量局部、可回滚。

建议命令：

```bash
git status --short || true
git ls-files || true
```

### 阶段 2：项目结构盘点

Codex 应识别：

1. 项目类型，例如前端、后端、全栈、脚本库、monorepo、移动端、数据项目等。
2. 包管理器或构建工具，例如 npm、pnpm、yarn、uv、pip、poetry、go、cargo、maven、gradle 等。
3. 核心目录。
4. 测试目录。
5. 配置目录。
6. 文档目录。
7. 不应处理的生成目录和依赖目录。

Codex 应把识别结果用于 README 内容，不要照搬模板空话。

### 阶段 3：创建或更新 `AGENTS.md`

执行规则：

1. 如果不存在 `AGENTS.md`，创建完整版本。
2. 如果已存在 `AGENTS.md`，保留原有规则，将 README First 规则合并进去。
3. 如果原有规则与本方案冲突，不要删除；在文件中增加“冲突说明”或更高优先级的澄清。
4. `AGENTS.md` 中必须明确要求 AI 先读 README，做完记录。

### 阶段 4：创建 `.ai/` 记录体系

执行规则：

1. 创建 `.ai/changes/`。
2. 创建 `.ai/changes/YYYY-MM-DD.md`。
3. 创建 `.ai/decisions/`。
4. 创建 `.ai/decisions/0001-readme-first-policy.md`。
5. 不写入密钥、账号、内部敏感信息。

### 阶段 5：创建或补全根目录 `README.md`

执行规则：

1. 如果根 README 已存在，保留原有内容。
2. 只补充缺失的项目结构、运行方式、AI 协作规则。
3. 如果运行命令无法确认，写“待确认”，不要猜。
4. 不要把根 README 改成冗长手册。

### 阶段 6：为关键目录创建或补全 README

执行规则：

1. 先识别候选关键目录。
2. 对每个候选目录，读取目录内主要文件和子目录。
3. 判断该目录是否值得创建 README。
4. 如果值得，创建或补全该目录 `README.md`。
5. 如果已有 README，保留原内容并整理补充，不要粗暴覆盖。
6. 每个 README 应尽量短而准确，优先 300 到 1000 字之间。复杂目录可以更长，但必须保持可维护。

### 阶段 7：记录本次变更

在 `.ai/changes/YYYY-MM-DD.md` 中写入本次实施记录，必须列出：

1. 新增文件。
2. 修改文件。
3. README 覆盖范围。
4. 跳过目录。
5. 后续注意事项。

### 阶段 8：验证

Codex 应验证：

1. `AGENTS.md` 存在，并包含 README First 规则。
2. `.ai/changes/` 存在，并有当前日期记录。
3. `.ai/decisions/0001-readme-first-policy.md` 存在。
4. 关键目录 README 存在且非空。
5. 没有为明显生成目录、依赖目录、缓存目录创建 README。
6. Git diff 中不包含业务代码改动。

建议命令：

```bash
git status --short
git diff --stat
git diff --name-only
```

如果项目有文档 lint 或格式化命令，可以运行；否则不需要额外安装工具。

## 8. README 内容质量标准

每个目录 README 应满足：

1. 基于实际文件结构，不编造。
2. 明确目录职责。
3. 明确不负责什么，避免边界模糊。
4. 列出核心文件或子目录。
5. 说明对外接口或被其他模块使用的方式。
6. 说明维护约定。
7. 说明验证方式。
8. 包含 AI 操作提示。
9. 不包含密钥、令牌、密码、内部敏感数据。
10. 不包含无长期价值的修改流水账。

不合格示例：

```md
# utils

这里是工具函数目录。
```

合格示例：

```md
# 目录说明：utils

## 1. 目录职责

本目录存放跨模块复用的纯工具函数，主要用于字符串、日期、格式化、校验等无业务状态逻辑。

本目录不负责：

- 发起网络请求。
- 管理 UI 状态。
- 直接读取路由或浏览器全局状态。

## 2. 核心文件与子目录

| 文件/子目录 | 作用 |
|---|---|
| `format.ts` | 通用格式化函数 |
| `validate.ts` | 通用校验函数 |
| `index.ts` | 对外统一导出 |

## 3. 维护约定

1. 工具函数应尽量保持纯函数。
2. 新增公共工具函数后，应通过 `index.ts` 导出。
3. 不要在本目录中加入强业务语义逻辑，业务规则应放入对应 feature 或 service 目录。

## 4. AI 操作提示

AI 修改本目录前必须检查是否已有类似工具函数，避免重复实现。
```
